# Claude Code Engineering Guidelines: Lumement

This file serves as the permanent system configuration and architectural authority for the "Lumement" codebase. Every file creation, modification, and optimization step must strictly adhere to these parameters.

## 🔋 1. Core Philosophy: Zero-Idle Battery Profile
- **Headless & Reactive:** Lumement must consume exactly 0% CPU cycles when the device is idle.
- **No Background Loops:** No long-running coroutines, infinite `while` loops, or persistent background threads while the panel is dark. The only loops are frame-driven animations (the LED breath, the arrival effect) that run while the glow screen is lit, and they end with it.
- **Event-Driven Only:** The app only wakes up when the system calls it: `onNotificationPosted`/`onNotificationRemoved`, screen on/off, unlock, display changes. Timers are short, bounded one-shots on a `Handler`.
- **Hardware Release:** Every wake lock is acquired with a timeout (or released when the LED leaves the front). Once all waiting messages are read, the glow screen finishes and the CPU falls back to deep sleep.
- **The lit screen is budgeted:** a screen held on for the LED costs the S23 175-189 mA, and its power profile puts a lit screen's floor near 100 mA, so no tuning makes it cheap. The LED holds the screen on only in its bright phase after a new message (`Bright.kt`: 10 min by default, started over by each message, 30 min per unread streak at most, never in Battery Saver or below 20%), then the phone sleeps into One UI's always-on display with the LED still on it (88 mA measured, the CPU asleep), or the LED goes dark. When the system ends its always-on display by itself, the LED goes dark with it; it never lights the screen in its place.

## 🛡️ 2. Privacy & Permission Boundary
- **Minimal Surface Area:** Request the absolute fewest permissions required by the OS. No internet, no telemetry.
- **Forbidden Permissions:** Do NOT introduce `SYSTEM_ALERT_WINDOW` (Draw over other apps). This avoids heavy window manager overhead and prevents the app from being killed by aggressive OEM battery managers (like Samsung's App Power Management). No `QUERY_ALL_PACKAGES` either: the manifest's `<queries>` covers launcher apps (app icons, and the Apps screen's list of other apps).
- **Approved Permissions:**
  - `android.permission.WAKE_LOCK` (To cleanly illuminate the physical panel).
  - `android.permission.POST_NOTIFICATIONS` (The bridge notification that carries the full-screen intent; Android 13+ runtime grant).
  - `android.permission.USE_FULL_SCREEN_INTENT` (The only background-launch path Android allows without `SYSTEM_ALERT_WINDOW`).
  - `android.permission.BIND_NOTIFICATION_LISTENER_SERVICE` (System-enforced access boundary).
  - `com.android.vending.BILLING` (from Play Billing: premium is bought through the Play Store app over IPC). Billing's telemetry (`com.google.android.datatransport`) is excluded in `app/build.gradle.kts`: it would add `INTERNET` and background upload jobs, and billing skips logging without it. `make permissions` (part of `make check`) fails if the release APK asks for `INTERNET` or `ACCESS_NETWORK_STATE`.
  - `android.permission.BIND_ACCESSIBILITY_SERVICE` — optional, user-enabled `GlowShield` only: `TYPE_ACCESSIBILITY_OVERLAY` windows for short moments — the see-through arrival effect over the lit lock screen (no app window can draw above a visible keyguard), a black cover for the ~0.5 s LED wake hand-over, because One UI draws its status/navigation bars above every app window during that moment, and the lit LED's own window over the lock screen, which holds the window focus so One UI shows no fingerprint icon over the black while the lock screen waits ready under it (a power press, a sleep request on the lit phone, is cancelled and the window lifted; a finger down hands the lock screen the focus, so the fingerprint unlocks). Plus `GLOBAL_ACTION_LOCK_SCREEN` to put the phone to sleep at once when the LED has nothing left to show (read elsewhere, Do Not Disturb, put away face down). Where the always-on display shows, a see-through window over it instead, put up while the screen is on (One UI draws no app window while dozing): the LED rises once in its SurfaceView and stays still, the panel holding the frame in DOZE_SUSPEND with the CPU asleep, with `PowerManager.DRAW_WAKE_LOCK` (a level of `WAKE_LOCK`, no extra permission) through each rise so the panel takes frames; an alarm allowed while idle moves it a step every 10 minutes (burn-in). No event types, no window content.

## 🚀 3. High-Performance Execution & Memory Rules
- **Avoid GC Trashing:** During `onNotificationPosted`, converting an app icon to a bitmap can trigger aggressive Garbage Collection (GC) pauses if done inefficiently. `BrandColors` reuses one 96 px bitmap per listener connection; keep it that way.
- **Lock-Screen Windows:** The glow screen is a `ComponentActivity` that switches `setShowWhenLocked` at runtime to cover or uncover the lock screen in place. It never arms `setTurnScreenOn` except as the full-screen-intent fallback; `PanelWaker` (a short screen wake lock) does every wake.
- **Draw-Phase Discipline:** Build brushes, shaders, strokes and paths once in `drawWithCache`; per frame only read the clock and move what was built (shader uniforms, local matrices, alpha). Never allocate in `onDraw*`. Animated values are read in the draw or layout phase, so a frame never recomposes. Runtime shaders (AGSL) are Android 13+; every one has a gradient fallback below that.
- **The LED breathes without redraws:** on Android 10+ the glow screen's LED, the lit LED's window and the always-on display's are a `LedSurface` (`LedSurface.kt`): drawn into a SurfaceView of their own once per breath (each step only for a material that moves), breathed by the surface's alpha on the compositor. On the always-on display it rises once and holds still (`LedSurface.glow`): each breath there pulled the panel out of DOZE_SUSPEND and cost 42 mA. Compose draws the LED only below Android 10 and in the dashboard previews.
- **Timing Is a Signal:** The live effect and the LED keep real time (`RealTimeMotion`) whatever the animator duration scale. Dashboard chrome follows the system scale (`GlowMotion`).

## 📁 4. Architecture Requirements
- **Build System:** compileSdk 37, targetSdk 36, minSdk 26, Kotlin DSL (`.gradle.kts`) with a version catalog.
- **UI Framework:** Jetpack Compose using the modern Bill of Materials (BOM) management.
- **Color Extraction:** `androidx.palette:palette-ktx` for ultra-fast, high-precision extraction.
- **R8 Optimization:** ProGuard rules must enforce aggressive shrinking and obfuscation to keep the runtime DEX footprint as tiny as possible. Log through `GlowLog.d { "..." }`: the lambda sits behind `BuildConfig.DEBUG`, so release builds never build the message or run the reads (binder calls) inside it.

## 🗺️ 5. Code Map
- **Settings:** `GlowSettings.kt` (every option, as `Labeled` enums, and the `GlowSettings` defaults), `GlowPrefs.kt` (storage).
- **Runtime state:** `GlowSession.kt` — `GlowPending` (unread messages), `GlowSession` (listener ↔ glow screen link; `resting` while Do Not Disturb is on; `bright`, the unread streak's bright phases), `WakeMode`. `Bright.kt` — `BrightStreak` (the bright phase after a message and the streak that caps it), `litLedAllowed` (may the LED hold the screen on now).
- **LED diary (debug builds only):** `LedDiary.kt` writes what the LED does and when the user looks (message, read, screen on/off, Lumement's own wakes and launches, peek, unlock, the bright phase's end, the LED onto and off the always-on display) to a local file, times and events only; the lock flow writes through `LockPort.note`. `make diary` pulls it and `scripts/diary.py` turns it into the defaults (first looks within 5/10/15 min, streak spread, how long One UI kept its always-on display); release builds compile it away.
- **Apps:** `GlowApps.kt` (its own prefs file, which the listener learns apps into: muted/colour choices, look-alikes, launcher-list search). Kept apart from `GlowPrefs`, because the dashboard saves settings whole.
- **Wake path:** `NotificationWakerService` (filters messages with `MessageFilter.kt`, skips muted apps, `GlowApps` colour or `BrandColors`) → `GlowLauncher` (bridge notification + full-screen intent) → `WakeScreenActivity` (the window and the phone: system services, wake locks, timers, broadcasts, as a `LockPort`) running `LockFlow.kt` (the lock flow state machine, plain Kotlin) and drawing `GlowScreen.kt` (the LED round, the arrival on black). `Power.kt`: `PanelWaker`, `DarkHold`, `inCall`, `AfterCall`. When the listener relights, and the watchdog's check: `relightPlan`, `ledMissing` in `GlowSession.kt`.
- **Glow screen helpers:** `Led.kt` (breath curve, `LedDot`: a dot, a ring round the camera or a frame round the screen's edge (`LedForm`), the round's timing and burn-in steps), `LedSurface.kt` (the LED in its own surface), `LedLook.kt` (what the LED is made of: neon, or the Edge Frame's element, shared by the LED and the hand-off landing on it; the frame LED is the Edge Frame waiting, always plain light (its colours, line and glow, quieter, calming over the bright phase; never an element or running light: a full-edge repaint per step lags at the LED's frame rate)), `LedWindow.kt` (bars, display modes), `RelightLimiter.kt`, `Stowing.kt` (put away: face down and still, or covered; taken out again; picked up with the LED lit, if the system's lift to wake is on: the system's own lift listens only while the phone sleeps).
- **Effect:** `ArrivalEffect.kt` (timeline + drawing), `CrestShader.kt`, `FrostShader.kt` (Water), `FireWave.kt` + `FireShader.kt` (Fire: timeline, palette, shader), `AirWave.kt` + `AirShader.kt` (Air: timeline, whirl, palette, shader), `EarthWave.kt` + `EarthShader.kt` (Earth: timeline, impact, shake, palette, shader), `EdgeLight.kt` + `ElementFrame.kt` + `HandOff.kt` + `LandingTouch.kt` (Edge Frame: comet heads, the frame made of the element, its last light becoming the LED: token, ring or flight, a small touch of its element as it lands (`LandingTouch`), then the LED's first exhale, which the Edge Frame's length runs on through: `arrivalMsFor`), `FrameLanding.kt` (arrivals ending in the frame LED: the Edge Frame settling into it, the beacon's light running round the edge to lay it), `GlassHaze.kt`, with `ShaderBrushes.kt`, `Oklab.kt`, `GlowMath.kt`, `GlowRenderer.kt` (geometry, `GlowGraphic`).
- **Premium:** `Premium.kt` (where it stands: `PremiumState`, the 7-day trial counted from the first message it plays for, `playable` (a premium element arrives as Water after the trial), its own prefs file), `dashboard/PremiumModel.kt` (the only code that talks to Google Play, while the dashboard is up; stores what Play says) + `dashboard/PremiumViews.kt` (`PremiumLine`, `PremiumStatus`, `PremiumOverCard`) + `dashboard/PremiumScreen.kt` (the Premium page from the header's sparkle, which is gone once owned: what it adds, paid once, what stays free, the buy button). Premium is Fire, Air, Earth and an app's own colour. New installs start on Air (Android 13+, `firstElement`), so every new user gets the trial with their first message; everything else is free, including keeping look-alike apps apart (`settled` in `GlowApps.kt`). The glow screen and overlay read `GlowPrefs.loadPlaying`. `make install-premium` / `make release-premium` (or `PREMIUM=1` on any target) build with premium unlocked for good (`BuildConfig.PREMIUM`); `TRIAL=untried|1..7|over` (`make install-trial-over`) stages the trial whatever the clock says (`BuildConfig.TRIAL`, writes nothing). `make bundle` refuses both. Prompts: at most one per dashboard open and never in setup: the trial-over card once, or else Play's in-app review once ever, never in premium's way: not during the trial, a week after it ended if not bought, else a week after the first app was heard from (`reviewDue` in `dashboard/ReviewAsk.kt`). After the trial, tapping a locked colour opens the purchase sheet. Never a notification for either: ours would light the screen and the LED.
- **Overlay:** `GlowShield` (accessibility overlay: effect over the lock screen, wake cover, blur, the lit LED's window with the lock screen ready under it, the LED on the always-on display: `AodLed.kt` (`LedRound`: the round, breathing over the lit panel, still on the always-on display)). When the LED goes in its window and when it makes way: `ledWindowWanted`, `ledWindowEnds` in `GlowSession.kt`. Whether a sleep shows the always-on display: the listener watches every sleep (`NotificationWakerService.watchSleep`, `sleepShowsAod`), and the system's own switch (`aodSetting`) says when that answer is stale (`sleepWillDoze`, `GlowSession.expectsAod`); with no glow screen up, it relights onto the always-on display without a wake (`WakeMode.AOD`).
- **Dashboard:** `MainActivity` → `dashboard/` (`Dashboard`, `AppsModel` + `AppsScreen` + `AppRow` (the Apps screen from the header), `Access`, `EffectCard`, `ElementCard` + `WaterOptions`, `FireOptions`, `AirOptions`, `EarthOptions` (built from `GlyphTiles`), `LedCard`, `LedShowcase`, `PhoneMock`), built from `ui/components/` (`Controls`, `Chips`) and `ui/theme/`.

## 🧩 6. Conventions
- **Adding a setting:** a field with its default in `GlowSettings`, and one line each in `GlowPrefs.load` and `GlowPrefs.save`. Options are enums implementing `Labeled`, so `ChipRow` lists them as they are. If the arrival effect reads it, check `forPreview()`.
- **Pure logic goes where it can be tested:** curves, geometry, rate limits and colour maths are plain functions or small classes with unit tests in `app/src/test`. Run `make test`; `make check` runs lint, tests and both builds.
- **The lock flow is tested on a simulated phone:** `LockFlowTest` drives `LockFlow` on `FakePhone` (One UI's measured timings, the screen timeout and its trap, GlowShield), and checks after every step that the LED's face and window are never both up and no screen lock outlives the session. A lock-flow change comes with a scenario; a bug from the phone becomes one first. `LockFlowFuzzTest` plays seeded random phones and users against the same promises (no screen lock after all read or after the bright phase, never relighting for a dropped AOD, the streak's cap, no timer in the dark long after anything happened); a failure prints its seed and trace, and `FUZZ_SEED=n` (with `--rerun`) replays it. `FakePhone` plays each glow screen as its own activity.
- **Shared visuals live once:** the LED's look (`LedDot`, `LedLook`, `ledBreathAt`), the camera position (`ScreenGeometry.lens`), motion specs (`GlowMotion`) and dashboard controls (`ui/components`) are reused by the glow screen, the overlay and the dashboard previews alike.
